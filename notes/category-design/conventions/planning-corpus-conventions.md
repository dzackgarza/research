## OPINIONATED 5-PHASE METHODOLOGY FOR CATEGORY REFACTORING

When working on SageMath category refactoring (or similar complex structural changes), agents MUST follow this careful 5-phase approach with built-in strategic stops:

### PHASE 1 - ANALYSIS: Document current state
1.1 Catalog all sections in the target file (identify mixed implementations)
1.2 List all methods and identify where they properly belong (ParentMethods, ElementMethods, HomsetMethods, etc)
1.3 Trace dependencies - what other files reference the old vs new patterns
**STOP 1**: Sequential thinking - Review analysis findings, verify understanding before proceeding

### PHASE 2 - DESIGN: Create detailed refactoring architecture  
2.1 Design the Category class structure (inheritance, inner classes, methods)
2.2 Design the Parent class structure (what it inherits, what it implements)
2.3 Design the Element class structure (base classes, methods)
2.4 Design factory functions and user-facing API
**STOP 2**: Review design with zen consensus tool - get external validation of approach

### PHASE 3 - COMPATIBILITY: Plan smooth transition
3.1 Find all current usage patterns in examples and tests
3.2 Design compatibility layer for backward compatibility during transition
3.3 Create migration guide documenting how to update old code
**STOP 3**: Sequential thinking - Verify no breaking changes, all patterns covered

### PHASE 4 - DOCUMENTATION: Update documentation structure
4.1 Split/reorganize documentation files to match new structure
4.2 Update all examples to use new patterns
4.3 Convert mathematical assertions to proper doctests following TDD principles
**STOP 4**: Review documentation changes - ensure clarity and completeness

### PHASE 5 - VALIDATION: Final checks before implementation
5.1 Review against SageMath category framework checklist
5.2 Verify consistency with other category implementations in SageMath
5.3 Define comprehensive test strategy for the refactoring
**STOP 5**: Final review with zen thinkdeep - comprehensive validation

### Key Principles of This Methodology:

1. **Strategic Stops**: Each phase ends with a mandatory stop for reflection and validation. This prevents rushing and ensures quality.

2. **Non-Destructive**: All work is documented in planning files. No existing code is modified during planning phases.

3. **External Validation**: Use zen tools (consensus, thinkdeep) at critical decision points to catch issues early.

4. **Sequential Thinking**: Force pauses for sequential reasoning to avoid overlooking critical details.

5. **Documentation First**: All changes are fully documented before any implementation begins.

### Example Usage:

When an agent encounters a category refactoring task like "Refactor RMod from Parent to Category class":

1. First create/update a FEATURE planning document 
2. Use TodoWrite to create the full 5-phase task list with all subtasks
3. Work through phases methodically, documenting findings at each step
4. Use the STOP points to pause, reflect, and validate before proceeding
5. Only after Phase 5 completion should any actual code changes be considered

This methodology ensures thorough analysis, prevents common pitfalls, and maintains the mathematical rigor required for SageMath development.
